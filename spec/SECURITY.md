# 보안 정책 및 검증 범위

## 작성자 익명성

소셜 로그인은 메시지 등록 전에 필요합니다. `public.messages.sender_id`에 작성자 ID를 저장해
같은 캘린더·날짜·계정 조합의 메시지 중복을 DB 고유 인덱스로 방지합니다.
작성자 ID 컬럼의 SELECT/INSERT 권한은 클라이언트에서 제거하고, DB가 `auth.uid()`로 채웁니다.
캘린더 주인은 작성자의 로그인 식별자를 조회할 수 없습니다.
다만 Supabase 플랫폼 자체의 인증/접속 로그까지 지우는 의미는 아닙니다.

## RLS 기반 잠금

- `calendars`: 공개 조회만 허용, 새 캘린더는 `owner_id = auth.uid()` 조건으로 생성.
- `messages`: 익명 사용자에게 SELECT/INSERT 권한을 부여하지 않습니다.
- `messages`: 로그인한 사용자만 지정된 시즌 기간 중에 등록할 수 있습니다.
- `messages`: SELECT는 캘린더 주인에게만, 그리고 날짜가 된 글에만 허용합니다.
- 미래 날짜 메시지는 API 응답, 개수 조회에서도 제외되어야 합니다.
- 비밀번호·권한 확인을 브라우저의 UI 전환만으로 처리하지 않습니다.

## 데이터 정합성

- 달력 닉네임 1~12자, 메시지 1~200자, 초콜릿 0~5 선택
- 날짜 2026-11-05 ~ 2026-12-25만 허용
- 12월 25일 이후 INSERT 불가 (KST)
- 메시지 한 건에는 정확히 한 날짜와 초콜릿이 저장됨
- 작성자별 캘린더·날짜당 한 개, 자신의 메시지만 조회·수정·삭제 허용
- 본인 메시지 조회 RPC는 작성자의 세션 ID로만 필터링하며 작성자 ID를 반환하지 않음
- 새 캘린더는 랜덤 URL 식별자(16자리)를 생성
- UI 출력은 HTML 이스케이프를 거침

## 적용 및 검증 기록 (2026-11-03)

Dear Choco 전용 Supabase 프로젝트 `lrpehigfvwddizepghnc`에
`dear_choco_initial_calendars_messages` 마이그레이션을 적용했습니다.

- `public.calendars`, `public.messages` 생성과 RLS 활성화를 확인했습니다.
- 네 개의 RLS 정책 적용과 소유자 계정의 캘린더 INSERT를 롤백 트랜잭션으로 검증했습니다.
- 미래 날짜 메시지는 소유자 인증 컨텍스트에서도 SELECT 0건으로 검증했습니다.
- 시험 데이터는 모두 ROLLBACK해 실제 사용자 데이터로 남기지 않았습니다.
- 정적 테스트는 날짜·라우팅·이스케이프·SQL 정책, 브라우저 모의 테스트는
  로그인 복귀·생성·작성·열람·잠금·다중 메시지 이동을 검사하도록 작성했습니다.

실제 카카오·구글 OAuth, 다른 두 사용자 사이의 메시지 전달 및 배포 도메인 설정은
각 사용자 브라우저에서 별도로 점검해야 합니다. 로컬 통합 테스트만으로
외부 OAuth 제공자와 실제 날짜 경계를 보증할 수는 없습니다.

비밀번호나 OAuth Secret을 이 저장소에 업로드하지 마세요.
