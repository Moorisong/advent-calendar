# 보안 정책 및 검증 범위

## 작성자 익명성

소셜 로그인은 메시지 등록 전에 필요하지만, `public.messages`에는 작성자 계정 ID를 저장하지 않습니다.
따라서 캘린더 주인은 DB 조회로도 작성자의 로그인 식별자를 얻을 수 없습니다.
다만 Supabase 플랫폼 자체의 인증/접속 로그까지 지우는 의미는 아닙니다.

## RLS 기반 잠금

- `calendars`: 공개 조회만 허용, 새 캘린더는 `owner_id = auth.uid()` 조건으로 생성.
- `messages`: 익명 사용자에게 SELECT/INSERT 권한을 부여하지 않습니다.
- `messages`: 로그인한 사용자만 지정된 시즌 기간 중에 등록할 수 있습니다.
- `messages`: SELECT는 캘린더 주인에게만, 그리고 날짜가 된 글에만 허용합니다.
- 미래 날짜 메시지는 API 응답, 개수 조회에서도 제외되어야 합니다.
- 비밀번호·권한 확인을 브라우저의 UI 전환만으로 처리하지 않습니다.

## 데이터 정합성

- 달력 닉네임 1~12자, 메시지 1~200자, 초콜릿 0~5 선택
- 날짜 2026-11-05 ~ 2026-12-25만 허용
- 12월 25일 이후 INSERT 불가 (KST)
- 메시지 한 건에는 정확히 한 날짜와 초콜릿이 저장됨
- 새 캘린더는 랜덤 URL 식별자(16자리)를 생성
- UI 출력은 HTML 이스케이프를 거침

## 배포 전 추가 확인이 필요한 부분

이 작업 환경에는 Dear Choco 전용 Supabase 프로젝트가 아직 없습니다.
따라서 SQL은 준비했지만 **실제 프로젝트에 적용하지 않았으며**, 실DB RLS 정책 실행 및
OAuth 제공자의 실제 인증 왕복 테스트는 아직 검증할 수 없습니다.

`npm test`는 날짜·라우팅·이스케이프·정적 SQL 정책 검사를 수행합니다.
DB 설정 후에는 서로 다른 계정에서 권한 경계를 반드시 실환경 검증하세요.

비밀번호나 OAuth Secret을 이 저장소에 업로드하지 마세요.
